# 進め方のルール

このプロジェクトの目的は、**古典的レイトレーシングから現代の技術までを、自分の手で実装しながら、何が行われているかを理解すること**。
速く作ることよりも、1歩ごとに「何が変わったか」を説明できることを優先する。
全体の計画は [RENDERER_ROADMAP.md](RENDERER_ROADMAP.md)、実装の現状は [CURRENT_IMPLEMENTATION.md](CURRENT_IMPLEMENTATION.md)、作業の履歴は [WORKLOG.md](WORKLOG.md) にある。

## ドキュメントの役割

| ファイル | 内容 | 更新するタイミング |
|---|---|---|
| `docs/RENDERER_ROADMAP.md` | マイルストーン、チェック欄、現在地、実験ログ | タスク完了時 |
| `docs/CURRENT_IMPLEMENTATION.md` | **今のコードが何をしているか**(仕様・制約・既知の問題) | 実装を変えたとき(必ず) |
| `docs/WORKLOG.md` | **いつ・何をしたか**、到達点、次の一手 | 作業の終わり(毎回) |
| `docs/WORKFLOW.md` | このファイル。進め方のルール | ルールを変えるとき |

ロードマップは「これからの計画」、CURRENT_IMPLEMENTATION は「今の事実」、WORKLOG は「過去の記録」。混ぜない。

## 1回の作業の流れ

1. **現在地を確認する**: ロードマップの「現在地」と、WORKLOG の最新の「到達点・次の一手」を読む。
2. **タスクを1つ選ぶ**: 一度に追加する概念は1つだけ。何が変わるはずか、どう確かめるかを先に決める。
3. **既存コードを確認する**: 推測で決めつけず、読んでから変更する。変更は必要最小限にする。
4. **実装する**: 古い方式は残し、新しい方式はスイッチで切り替えられるようにする(比較のため)。
5. **確認する**: ビルド、テスト、レンダリング画像を確認する。数値は**測ったものだけ**を書く。
6. **理解のために説明する**: 「この処理で何が起きているか」「昔の手法とどう違うか」を、コードを読まなくても分かる程度に説明する(作業の報告か、ログに書く)。
7. **記録する**: WORKLOG に追記する。実装が変わったなら CURRENT_IMPLEMENTATION を更新する。完了条件に達したタスクは、ロードマップのチェック欄を更新する。

## 記録のルール

- **未確認は未確認と書く**。測っていない数値、動かしていない機能を、完了・実測として書かない。
- 実装されていると確認できない機能を、勝手に完了扱いにしない。
- 画像で比べるときは、解像度・サンプル数・乱数シード・反射回数・光源などの**設定を一緒に記録**する(ロードマップ「比較実験の共通ルール」に従う)。
- 実験の成果物は `experiments/YYYY-MM-DD_名前/` に置く(設定、画像、メモ)。
- バイアス・近似・制限は、見つけた時点で CURRENT_IMPLEMENTATION の「既知の制約」に書く。

## 実装の約束

- 計算は**線形色空間**で行い、sRGB変換などの表示処理は最後に分ける。
- 新しい最適化や手法は、無効化できるスイッチを付ける。
- 正しさを先に、速さは後に。まず単純な参照実装を作る。
- 全面的な書き換えを先にしない。

## 役割分担

- Blender は、シーン作成と(比較用の)Cycles に使う。自作の光輸送を Cycles に任せない。
- Blender の MCP 操作、シーンのエクスポート、レンダラの実装は、別の作業として混同しない。
- Blender の `.blend` を保存するときは、上書きになることを意識する(直前の版が `.blend1` に残る)。

## Git・公開のルール

- **プッシュは、依頼があったときだけ行う**。
- 公開前に、含めるファイルを確認する。個人情報(メールアドレス、ローカルパス、認証情報)や、他人の権利を侵害しうるファイルを入れない。
- コミットの作者メールには、GitHub の noreply アドレスを使う(このリポジトリのローカル設定済み)。
- `.gitignore` の方針: `build/`、出力画像、`.blend` / `.blend1`、`.mcp.json`、エディタ・OS の一時ファイルは含めない。モデルやシーンは GLB で共有する。
- 外部のモデル・テクスチャ・HDRI を使うときは、ライセンスを確認し、出典を記録する。

## WORKLOG の書き方

`docs/WORKLOG.md` の先頭(新しいものを上)に、日付ごとのセクションを追加する。

```markdown
## YYYY-MM-DD

### やったこと
- ...

### 到達点
- 今どこまでできているか(1〜3行)

### 気づき・つまずき
- ...

### 次の一手
- ...
```

マイルストーンに関わる作業なら、見出しに `[M0]` のようにIDを付ける。
